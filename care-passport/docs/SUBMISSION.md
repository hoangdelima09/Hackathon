## Official requirements versus project choices

| Official requirement | Care Passport evidence / current status |
|---|---|
| Small working prototype with TideCloak integrated; demonstrate a useful possibility beyond ordinary login/backend permissions | **Missing:** no implementation in this checkout |
| Public GitHub repository containing the working source | `hoangdelima09/Hackathon` is **public** (checked with `gh` on 22 Oct, 11:05). Runnable source still missing |
| README starts with the supplied Project overview template and answers five prompts; overview at most 300 words | Root [README](../../README.md) follows the template exactly; its text is honest about status and must be updated after the build |
| Two-minute `.mp4` video inside that repository, under 100 MB | **Missing:** only a [script](DEMO-SCENARIOS.md) exists |
| Submit the public repository link through the official Google Form | Not submitted; [submission form](https://forms.gle/HRHYjnqB86j1LFS97) |

The 300-word limit applies to the project overview, not the entire README including
setup. Keep setup in its own section. The badge/link and five numbered headings in
our README follow the template generated by the organiser's page.

The FAQ recommends synthetic data and mocked external systems for sensitive domains.
Care Passport therefore uses only synthetic medical records and fictional clinicians.
This does not justify mocking TideCloak for the core security demonstration.

The organiser does **not** mandate our `docs/` filenames, a `src/` directory,
`demo.mp4` as the exact filename, three scenarios, our API, a custom Forseti contract,
a deployed website, or using Tide MCP. Those are local implementation choices where
applicable. Example ideas are optional; Care Passport is one of the supplied ideas.

## Judging alignment

| Criterion | Weight | What the entry should demonstrate |
|---|---:|---|
| Vision & originality | 25% | Attribute the seed idea; differentiate through a concrete care handoff, named-recipient consent receipt and adversarial evidence |
| Trust constraint insight | 20% | Explain the authority the platform would otherwise retain and how the protected operation removes its unilateral power |
| Value & impact | 20% | Referral to GP, care plan to Physio, private pathology, patient-initiated withdrawal that no single admin can reverse |
| Why TideCloak matters | 20% | Per-record `RelationshipAttestation:1` policies enforced by the Tide network, plus quorum-governed membership; the leaked-copy test shows denial survives a bypass of app permissions |
| Prototype & storytelling | 15% | Working happy path, selected negative tests, clear two-minute narrative and accurate README |

No numeric score is assigned before there is an implemented demo to assess.

## Submission form fields

The [official form](https://forms.gle/HRHYjnqB86j1LFS97), inspected read-only on
22 October 2026, asks for three required fields:

1. Group name: `<university>_<campus>_<team>_C<challenge>`. Campus values shown are
   `SGS`, `HNI`, `MEL`, `MYS`; this entry is Challenge 2, so the suffix is `C2`.
2. Team email addresses; the form's example separates addresses with semicolons.
3. Public GitHub repository URL containing source code, README and video.

Prepare these values with the team. Member emails belong in the submission form,
not necessarily in the public repository. No form response was sent during review.

## Repository layout and discoverability

Decision (22 Oct): submit the parent repository `hoangdelima09/Hackathon` as is. The
**root** `README.md` carries the required overview (judges see it first) and links to
the app, setup and video. Layout:

```text
README.md               # Template overview (≤300 words), then Setup and links
demo.mp4                # Two-minute video (<100 MB)
CLAUDE.md, .mcp.json    # Agent instructions and Tide MCP config
care-passport/          # Next.js app from Tide's template + package-lock.json
care-passport/docs/     # Specifications, plan and measured evidence
```

`care-passport/README.md` is a short developer README. The overview lives only in the
root README, so the two cannot drift apart.

## Regional deadlines

The organiser config explicitly stores **separate deadlines by location**, and the
countdown selects one using the viewer's time zone. They are not a single instant
shown in different time zones.

| Location | Published local deadline | UTC instant |
|---|---|---|
| **Vietnam** | **Thursday 22 October 2026, 18:00 (UTC+7)** | 22 October, 11:00 UTC |
| Malaysia | Thursday 22 October 2026, 18:00 (UTC+8) | 22 October, 10:00 UTC |
| Melbourne | Friday 23 October 2026, 10:00 AEDT (UTC+11) | 22 October, 23:00 UTC |

For the Vietnam context, plan against **18:00 on 22/10/2026** and aim to submit the
form by **17:30**. Do not substitute Melbourne's later deadline. Check organiser updates before submission; local team
eligibility or an exception must come from the organisers. The hidden HTML text
“Submissions have closed” is not reliable evidence of current submission status:
the live script computes it per region and time.
